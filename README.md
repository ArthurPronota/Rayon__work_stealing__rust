# Rayon и work stealing в вычислительных задачах.

## Часть 1. Что такое Rayon

**Rayon** — это библиотека **параллельной обработки данных** для Rust, основанная на стратегии **work stealing**. Её главная сила — **адаптер `par_iter`**, который превращает **обычный итератор** в **параллельный** одной строкой.

```rust
use rayon::prelude::*;

let res = (0..1_000_000)
    .into_par_iter()      // ← обычный диапазон → параллельный итератор
    .map(|x| x * x)       // ← map выполняется параллельно
    .sum::<u64>();        // ← sum собирает результат
```

## Что делает `par_iter`

`par_iter` — это **ключевая абстракция** Rayon. Она:

- превращает **последовательный** итератор в **параллельный**;
- автоматически **делит работу** между потоками;
- **скрывает** от пользователя всю сложность управления потоками.

Есть три варианта:

| Метод | Что делает |
|---|---|
| `par_iter()` | Параллельный итератор по ссылкам (`&T`) |
| `par_iter_mut()` | Параллельный итератор по изменяемым ссылкам (`&mut T`) |
| `into_par_iter()` | Параллельный итератор с **владением** (`T`) |

## Разбор кода

### Пример 1: сумма квадратов

```rust
let res = (0..1_000_000)
    .into_par_iter()
    .map(|x| x * x)
    .sum::<u64>();

println!("{}", res);   // 333332833333500000
```

- `(0..1_000_000)` — диапазон из миллиона чисел.
- `.into_par_iter()` — превращает диапазон в **параллельный** итератор.
- `.map(|x| x * x)` — возводит каждое число в квадрат. **Выполняется параллельно** на нескольких потоках.
- `.sum::<u64>()` — суммирует результаты. Rayon **автоматически** разбивает сумму на части и складывает их.
- Результат: сумма квадратов от 0 до 999 999 = **333 332 833 333 500 000**.

### Пример 2: сбор в вектор

```rust
let v_res = [0, 1, 3, 4, 5]
    .par_iter()
    .map(|x| x * x)
    .collect::<Vec<_>>();

println!("{:?}", v_res);   // [0, 1, 9, 16, 25]
```

- `[0, 1, 3, 4, 5]` — массив.
- `.par_iter()` — параллельный итератор по **ссылкам**.
- `.map(|x| x * x)` — возводит в квадрат.
- `.collect::<Vec<_>>()` — собирает в вектор. Rayon **сохраняет порядок** элементов.

## Часть 2. Как Rayon делит работу

### Divide-and-conquer

Rayon **не раздаёт элементы по одному**. Он использует **рекурсивное деление пополам**:

1. **Берётся исходный итератор** (например, из 100 элементов).
2. **Делится на две примерно равные половины** (по 50 элементов).
3. **Каждая половина снова делится на две** (по 25) — и так далее.
4. Деление продолжается, пока размер куска не станет **меньше порога** (по умолчанию — 1 или несколько элементов).
5. Маленькие куски **отправляются** на выполнение разным потокам.

Это называется **divide-and-conquer** (разделяй и властвуй).

### Схема

```
Исходный диапазон: [0 .. 100]
                    /        \
              [0..50]         [50..100]
              /    \           /     \
         [0..25] [25..50] [50..75] [75..100]
           ...     ...       ...      ...
```

Каждый узел дерева — это **задача**, которая может выполняться **параллельно** с другими.

### Зачем именно так

- **Балансировка**: если одна половина медленнее, потоки всё равно загружены.
- **Минимум синхронизации**: потоки работают над **независимыми** кусками.
- **Хорошая локальность**: данные куска находятся рядом в памяти.

## Часть 3. Work stealing

### Что это

**Work stealing** — это **стратегия планирования**, при которой:

- у каждого потока есть **своя очередь задач**;
- поток берёт задачи **с головы** своей очереди;
- когда у потока **закончились** свои задачи, он **крадёт** задачу **с хвоста** очереди другого потока.

### Схема

```
Поток 1: [T1, T2, T3, T4]   ← берёт с головы (T1)
Поток 2: [T5, T6]           ← берёт с головы (T5)
Поток 3: []                 ← пусто → крадёт с хвоста Потока 1 (T4)
```

### Почему это эффективно

1. **Снижение конкуренции за общую очередь.** Если бы была одна общая очередь, все потоки боролись бы за неё (блокировки, cache contention). Свои очереди — **локальны**.

2. **Хорошая локальность.** Поток берёт **свежие** задачи с головы — они недавно добавлены, данные ещё в кэше.

3. **Распределение нагрузки.** Когда поток простаивает, он **крадёт** работу у занятых — это **автоматическая балансировка**.

4. **Эффективность при коротких задачах.** Кража с **хвоста** (самые старые задачи) снижает конфликты: вор и владелец работают с **разных концов** очереди.

### На каких принципах работают

Work stealing используется в:

- **Rayon** — параллельные итераторы;
- **Tokio** — многопоточный async runtime;
- **async-std** — асинхронный runtime;
- **Go runtime** — планировщик горутин;
- **Java ForkJoinPool** — параллельные задачи.

## Часть 4. Когда Rayon уместен

### Хорошо подходит

- **CPU-bound задачи** — вычисления, обработка данных, алгоритмы.
- **Обработка коллекций** — map, filter, reduce, sum.
- **Однородные задачи** — все элементы обрабатываются одинаково.
- **Независимые элементы** — результат одного не зависит от другого.

### Плохо подходит

- **IO-bound задачи** — сетевое взаимодействие, чтение файлов.
- **Смешанные нагрузки с блокировками** — если внутри `map` есть `Mutex::lock`, потоки будут блокироваться.
- **Задачи с сильной зависимостью между шагами** — если шаг N зависит от N-1, параллелизм невозможен.

### Типичная ловушка

```rust
// ❌ ПЛОХО: блокирующий IO в par_iter
let results: Vec<_> = urls
    .par_iter()
    .map(|url| {
        reqwest::blocking::get(url).unwrap()   // блокирует поток!
    })
    .collect();
```

Если внутри `map` встретится **блокирующий** вызов, поток пула **займётся ожиданием**, и параллелизм **деградирует**. Это типичная ошибка при смешении Rayon с синхронным IO.

**Правильно:** для IO используйте **Tokio** или **async-std**, а не Rayon.

## Часть 5. Практические выводы

### Если задачи короткие и однородные

Work stealing **справляется почти идеально** — Rayon сам разобьёт работу и сбалансирует нагрузку.

### Если задачи разной длины

**Избегайте слишком длинных задач** — они **тормозят балансировку**. Пока один поток занят длинной задачей, другие не могут её «украсть» (она уже выполняется). В итоге часть потоков простаивает.

**Решение:** разбить длинную задачу на более мелкие куски.

### Если задачи блокирующие

**Не используйте Rayon.** Rayon предполагает, что задачи **не блокируются**. Для блокирующих задач:

- **Tokio** — асинхронный runtime с `spawn_blocking`;
- **async-std** — аналогично.

В Tokio то же самое означает **не блокировать поток** — иначе work stealing не поможет.

## Итог

| Аспект | Rayon | Work stealing |
|---|---|---|
| Что это | Библиотека параллельной обработки данных | Стратегия планирования задач |
| Ключевая абстракция | `par_iter` | Своя очередь у каждого потока |
| Как делит работу | Divide-and-conquer (пополам) | Кража с хвоста чужой очереди |
| Хорошо для | CPU-bound, однородные задачи | Короткие, однородные задачи |
| Плохо для | IO, блокировки, зависимости | Длинные задачи, блокировки |
| Где используется | Rayon, Tokio, async-std, Go, Java | — |

### Ваш код

- `(0..1_000_000).into_par_iter().map(|x| x * x).sum()` — **классический** пример CPU-bound задачи. Rayon делит диапазон пополам, потоки считают квадраты, work stealing балансирует нагрузку.
- `[0, 1, 3, 4, 5].par_iter().map(|x| x * x).collect()` — параллельная обработка маленького массива. Rayon сохраняет порядок.
- Результат: `333332833333500000` и `[0, 1, 9, 16, 25]`.

**Главное правило:** Rayon — для **CPU-bound** задач над коллекциями. Для **IO** — Tokio. Смешивать их без осторожности — типичная ловушка.
